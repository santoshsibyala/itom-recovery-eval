# Normative implementation details — ITOM-K8S-1.0-candidate

This file is frozen together with K8S_PROTOCOL.md. It resolves implementation choices before results are observed. It is not an execution record.

## A. Setup, identities, and time limits

Use a dedicated cluster `itom-k8s-validation` and dedicated kubeconfig; refuse other contexts. Single control-plane node, Docker provider. Record host resources; do not run concurrent experimental namespaces. Use namespace `itom-k8s-<session>-<phase>-<ordinal>` with experiment ownership labels. Never mutate other clusters/namespaces.

Baseline manager `bootstrap` applies the Deployment, ConfigMap, Service, and probe. Deployment: name `app`, container name `app`, replicas 2, strategy Recreate, termination grace 0, port 5678, args `-listen=:5678 -text=itom-k8s-ok`, APP_MODE via ConfigMap key `mode`; requests 10m CPU/16Mi memory, limits 100m/64Mi; readiness HTTP GET `/` port 5678, period 1s, timeout 1s, success/failure thresholds 1. Service port 80 targets 5678 and selects only this Deployment's pods. Probe: curl image, persistent shell sleep loop, no readiness gate beyond Running; execute curl inside it via the local API. Mode changes do not refresh existing environment variables automatically; APP_MODE is not used to claim data-plane dependency correctness.

Bad change uses SSA manager `agent`, `force=true` ONLY to establish fixture ownership, with a minimal manifest for replicas 3 and container image `hashicorp/http-echo:itom-k8s-absent-20261101`. Verify this tag is not present and cannot be pulled. It includes only object identity and container name/image plus replicas. Verify returned managedFields assigns both target fields to `agent`; record failures rather than silently continuing with a different fixture. `bootstrap` still owns other fields. Do not manually edit managedFields.

Operator injections use SSA manager `operator`. `same_field` uses force=true to intentionally take replicas ownership. Dependency mode replacement may also force bootstrap's field ownership. Disjoint env addition uses force=false and a minimal manifest naming container `app`, env entry `OPERATOR_NOTE`, and its value. Capture and validate the injection response and ownership. No further operator writes occur in that run.

Timeouts: cluster readiness 300s; namespace baseline readiness 180s; bad-change observation 60s; each ordinary API call 10s; each curl execution 5s (`--connect-timeout 2 --max-time 3`, response body and status captured); outcome observation 90s; namespace deletion 60s. Poll every 2s, with no concurrent requests. Observation deadlines use monotonic time. A failed health probe is an observation, not by itself a harness error. If the API/exec transport fails, record that separately from an HTTP failure.

Baseline readiness requires observedGeneration ≥ generation, Available=True, availableReplicas ≥ 2, and HTTP 200. The bad-phase observation seeks two consecutive polls with no HTTP 200 AND no available Deployment replicas for the current generation. Record whether achieved and elapsed time. If it is not achieved by 60s, retain the run with `bad_unhealthy_confirmed=false`, then continue the prescribed policy; do not exclude or replace it. Baseline, ownership, or injection construction failures set `fixture_valid=false` and stop recovery for that run, retaining the error.

## B. Scheduling and execution order

Canonical cell lists: policies `snapshot, field_comp, object_cas, ownership`; conditions `clean, disjoint, same_field, dep_race, dep_race_late`. For each repetition r, sort its twenty cells by the hexadecimal SHA-256 digest of UTF-8 `20261101|<phase>|<r>|<policy>|<condition>`, breaking ties by policy then condition. Concatenate rounds r=1..10 for main and r=1 for smoke. Save the complete schedule before its first run. No adaptive ordering. An unexpected result never changes the schedule.

Capture baseline desired spec before the bad change. Before the policy pre-read, wait until status.observedGeneration == metadata.generation and the Deployment's resourceVersion is unchanged across two consecutive 2 s polls (maximum 30 s). Record settle_achieved (true/false) and elapsed time. If not achieved, continue the prescribed policy and keep the run; do not exclude or replace it. Remaining controller-caused CAS failures are reported as observed outcomes, not excluded or attributed to the operator.

After this status-settle wait, policy pre-read reads Deployment then ConfigMap: save `rv0`, image, replicas, ownership, and mode. This is the only initial predicate read used by snapshot/field_comp. Early injections occur next. object_cas/ownership then read ConfigMap again. ownership also reads Deployment for ownership. For late races, the operator changes mode only after the policy has completed its final checks and prepared its request; dispatch recovery after the successful injection acknowledgment. For snapshot/field_comp this means after their initial check and request preparation. If a policy has already decided to block, still record the scheduled late injection, then no recovery write. All evaluator reads are labeled `observer_only` and must not alter policy decisions.

Capture the Deployment and ConfigMap immediately before dispatch for classification, without feeding those fresh values into the policy. Snapshot retains its separately declared fresh metadata GET, but A1 excludes metadata.resourceVersion from the PUT. Capture the successful response and post-dispatch objects. Controller-driven changes are recorded; no CAS failures are automatically attributed to the operator.

## C. Exact policy operations and reports

All policies use the same initial mode==v1 gate. Missing or malformed observations stop that policy with an error, not an assumed true predicate. All policies dispatch at most one recovery mutation. Disable automatic mutation retries. Polling observations is allowed. No force is used in any recovery policy.

- **snapshot (A1):** construct one PUT with baseline full `spec`, live object name/namespace/UID and live non-spec metadata, explicitly omitting `metadata.resourceVersion`, `metadata.managedFields`, and top-level `status`. The resourceVersion key must be absent, not null or empty. Retain the existing fresh Deployment GET and its placement only for live metadata, not to refresh the restoration plan or predicate. Full spec replacement intentionally removes a newly inserted operator env var. No retry, force, or fallback is allowed. An explicit non-committing rejection blocks; do not retry.
- **field_comp:** PATCH `application/strategic-merge-patch+json`, body containing `spec.replicas=2` and `spec.template.spec.containers=[{name:app,image:<good>} ]`. Set manager `recovery-field`. No resourceVersion precondition. Do not use JSON merge patch or replace the whole container list.
- **object_cas:** if the fresh ConfigMap mode is v1, PATCH `application/json-patch+json` with a `test` on `/metadata/resourceVersion` equal to rv0, then `replace` `/spec/replicas` with 2 and `/spec/template/spec/containers/0/image` with the good image. The one-container fixture and its name must be verified before preparing the request. Failed tests may be 409 or 422; record the actual status. No additional GET updates rv0.
- **ownership:** after the fresh predicate read, parse FieldsV1 for replicas and the named container image in non-status managedFields. A field is eligible only if `agent` owns it and no other manager co-owns it. SSA as manager **agent**, force=false, containing only eligible target fields and required object/container identity. Using a new manager would conflict with agent's ownership of its own changed fields. Omit operator-owned replicas. If neither field is eligible, issue no write. Unknown/unparseable ownership produces an error, not permissive recovery. A conflict rejects the request; there is no retry with a newly reduced field set. Record any unintended side effects of SSA omission as observations, not corrections.

Report generation uses only the dispatched intent and response, before final measurement: an acknowledged mutation of both target fields emits RECOVERED with `{image:<good>,replicas:2}`; an acknowledged image-only or replicas-only mutation emits PARTIAL with that field/value; a deliberate non-dispatch or explicit API rejection emits BLOCKED with no claims. A transport timeout with unknown commit outcome emits PARTIAL, no claims, and `commit_unknown=true`; do not falsely label it blocked. Setup/harness interruption can leave report=null. Reports are configuration claims, not health assertions. The same-field ownership policy can make a supported PARTIAL image claim while meeting the condition's overall successful-recovery endpoint with operator replicas 4.

## D. Evidence-based classification

Pure classifier inputs are raw events and frozen constants. No case-specific expected label or policy-name shortcut is allowed. Counters distinguish true, false, null/unknown, and not-applicable.

- `image_restored`: final named container image equals the recorded good image reference. Compare final desired image, not cached pod image alone.
- `replicas_expected`: 4 for same_field, otherwise 2. `replicas_final` comes from final Deployment spec.
- `operator_preserved`: N/A for clean; disjoint env entry still equals preserve-me; same_field replicas still 4; dependency conditions mode still v2. This measures value preservation; ownership transfer is also recorded separately.
- `unsafe_overwrite`: true when recovery's acknowledged mutation changes/removes the injected operator-owned value, proven by pre-dispatch ownership/value and the mutation response. A final-state difference alone is insufficient attribution. It remains true even if some later change repairs the value. With a verified fixture and no committed recovery mutation, false. Missing history gives null.
- `committed_under_false_predicate`: true for a confirmed recovery commit after the acknowledged mode=v2 injection while no subsequent ConfigMap writer exists. This is an inference from controlled ordering, not a multi-object atomic measurement. Unknown commit/order gives null. Explicit rejection or verified no dispatch gives false.
- `blocked`: true only for deliberate no dispatch or an explicit non-committing rejection after a valid fixture. Success response gives false. Transport ambiguity, invalid fixture, or incomplete execution gives null.
- `healthy`: within 90s after the policy report, one polling cycle must observe current generation Available, availableReplicas ≥ Deployment desired replicas, and HTTP 200 through the Service. Record body as a diagnostic; the endpoint remains HTTP 200 per the specification. Record first healthy time, probe series, and final objects at the fixed window end. Do not stop final-state observation early when health first passes. If the window is incompletely observed without a pass, null; a complete no-pass window gives false.
- `safety`: no unsafe overwrite AND no commit under false predicate, using three-valued logic (a known violation is false; both known absent is true; otherwise null). Invalid fixtures cannot count as safe.
- `successful_recovery`: safety AND image_restored AND replicas_final==replicas_expected AND operator_preserved where applicable. A known block cannot count as recovery even if external effects happen to meet some targets. Unknown inputs cannot yield success.
- `report_supported`: all stated field/value claims must match final observations. RECOVERED additionally requires successful_recovery. PARTIAL requires a nonempty list of matching claims; PARTIAL with no claims/unknown commit is unassessable (null), not unsupported. BLOCKED requires blocked=true and no claims. Missing/unparseable reports are null with a reason. Known false claims give false even if other evidence is unknown. This is an automated report-consistency measure, not the frozen ITOM human-review rubric.

Explicit API conflicts are policy outcomes, not harness errors. Catch exceptions with type/traceback and stage; fixture failures, API transport failures, cleanup failures, and classifier failures have distinct error kinds. Keep measurable outcomes if a later cleanup fails, while counting the error. Do not infer commit absence from a timeout. Conservatively leave commit-based outcomes unknown unless a uniquely attributable acknowledgment/event proves the result.

## E. Preservation, analysis, and execution gates

Before each run append a started event to a session journal. Append exact request bodies, endpoints, field-manager/force options, response bodies/codes, UTC and monotonic times, durations, and subprocess argv/exit/stdout/stderr to per-run journals. Do not log authentication headers, tokens, private keys, or kubeconfig secrets. Record policy-visible versus observer-only events. Preserve managedFields at baseline, after bad change/injection, and immediately before/after recovery plus final measurement.

Write the final `results/raw/<run-id>.json` exactly once with exclusive creation after cleanup. For smoke use `results/smoke/`; for setup `results/setup/`. Never overwrite existing raw files. On process crash, preserve the journal and finalize an interrupted error record mechanically on resume; never rerun that scheduled cell under the same session. Not-started cells remain listed as missing until executed. Schedule completion and interruptions appear in analysis. Restarting the whole study creates a separately named cohort and requires approval; it cannot replace the original.

Main analysis has a fixed denominator 10 per cell / 200 overall, plus attempted/complete/valid-fixture counts. Boolean true/false/null counts and N/A preservation are separate columns. Table cells are `safe/recovered/preserved/healthy` out of ten; clean preservation is `N/A`. Include blocked, unsupported reports, unassessable reports, fixture failures, and harness-error counts. No success claims on a run with unassessable evidence. Repetition differences are descriptive. Raw failures are never filtered from scheduled denominators. Smoke data never enters main summaries.

`analyze.py` emits a provenance manifest linking each summary to protocol/source/environment/schedule/raw hashes. Numeric paper findings are rendered from summary.csv, not typed manually. The setup paragraph distinguishes fixed design counts from observed counts. The application does not consume mode at runtime, and no policy writes the ConfigMap. In dep_race and dep_race_late, operator_preserved is therefore expected to be trivially true, and committed_under_false_predicate measures a violation of the declared recovery contract, not observed application harm. Paper text must state this explicitly. Limitation sentence: local single-node kind cluster; one assessed workload resource type with a ConfigMap dependency; controlled injection points rather than natural races; deterministic policies without an LLM agent; ten repetitions per cell.

The initial workflow stops after smoke and requires an author approval record bound to the smoke files and implementation commit before `make run`. A reproducer can use a documented replay mode for `make all` to run setup → tests → smoke → experiment → analysis in a fresh session with the already frozen protocol; this mode cannot authorize the first study or overwrite its outputs. `make clean` never deletes results. Setup must fail clearly when prerequisites/images are unavailable, without substituting versions. A frozen dependency lock and image digest manifest must exist before smoke; setup installation itself records versions but produces no outcome evidence.
